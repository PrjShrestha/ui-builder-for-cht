## 1. Feasibility verdict

**Feasible in two slices.** The parser is already chain-aware **for a single combinator**: `parseRelevant` at `relevantParser.ts:112-134` paren-aware-splits the top level on one combinator via `splitOnCombinator` (lines 144-174). The choices fix is a pure read-only server scan + client merge with zero XLSForm writes.

**Two empirically-verified caveats correct v0.1's overclaims:**

1. **The serializer normalizes whitespace.** `serializeRelevant(parseRelevant("${a}='x' and ${b}>10"))` returns `"${a} = 'x' and ${b} > 10"` — NOT byte-identical to input — with `isRawFallback === false`. Same-combinator chains round-trip byte-stable **only when the input is already in canonical spacing** (spaces around operators, a space after the comma in `selected(...)`). For tighter human spacing the serializer silently reformats without flagging it. This is the dominant hand-authored form in real configs, so the round-trip contract must use a **parse→reserialize→compare self-check** (§3.1) instead of trusting the structured path blindly.

2. **`parseRelevant` short-circuits on mixed combinators BEFORE any split.** Lines 118-121: if both `\band\b` and `\bor\b` appear anywhere (paren-blind regex), it immediately returns a single `RawRule` with `isRawFallback:true`. Verified: `parseRelevant("(${a}='x' and ${b}>10) or ${c}='y'")` returns `isRawFallback:true`, 1 raw rule. Therefore `parseRelevantGrouped` **cannot** "delegate to parseRelevant internals" for grouped input — it must detect the outer parenthesized structure and split on the outer combinator itself, then parse each de-parenthesized subgroup (§4).

The **only** architecturally non-trivial piece is the grouped-expression parser, and the breaking-change risk it carries is fully mitigated by adding a separate entry point rather than widening the existing one (§3). With that mitigation, the blast radius of the parser work is the new FormEditor builder only.

## 3. Round-trip + breaking-change safety contract

This is the non-negotiable bar (per CLAUDE.md round-trip invariant). The builder MUST guarantee on every write to `row.extras[column]`:

### 3.1 Byte-stability via a parse→reserialize→compare self-check (MANDATORY)

The serializer canonicalizes spacing, so trusting the structured path blindly **silently reformats tight human input** (verified: `${a}='x' and ${b}>10` → `${a} = 'x' and ${b} > 10`, `isRawFallback:false`). To make byte-stability real:

- Add an internal self-check to **both** `parseRelevant` and `parseRelevantGrouped`: after building the structured result, re-serialize it and compare to the original trimmed input. **If they differ, discard the structured result and return a single `RawRule` carrying the original (trimmed) text, with `isRawFallback:true`.** This guarantees `serialize(parse(x)) === x.trim()` for every non-raw result, and that any expression whose canonical form differs from the author's spelling is preserved verbatim as raw rather than reformatted.
  - **Implementation note:** the self-check compares against `expr.trim()` (parser already trims at line 113). The cancel-safety/round-trip tests therefore assert against the trimmed input. Pre-existing leading/trailing whitespace in `row.extras` is already normalized by `trim()` today; this is unchanged behavior and not introduced here.
- After this change, structured (non-raw) byte-stability is guaranteed by construction. The §6 test buckets are split accordingly: **canonical-spacing strings** assert structured stability; **non-canonical hand-written strings** assert `isRawFallback:true` AND that the raw text serializes byte-identical.

### 3.2 No partial clauses
`+ insert` disabled unless every clause in `clauses[]` AND the non-empty draft has `field`, `op`, and (for ops requiring it) `value`. Per-clause red border + `aria-invalid="true"` on the offender.

### 3.3 No silent connector mixing — serializer-side guarantee, not just a UI gate
A `ParsedExpression` has exactly one combinator; only `GroupedExpression` introduces a second. There must be **no code path** where mixed-combinator rules land in a single `ParsedExpression.rules[]` and serialize as flat `a or b and c`. Flat-mixed (no parens) is refused at the reducer (`commitClause('or')` while `lockedConnector==='and'` is a no-op in flat mode) AND structurally impossible at the serializer. The user mixes AND/OR only by explicitly creating a group. The legacy `build()`/`doInsert` fragment-append path (which *can* emit flat-mixed today) is deleted (§3.7).

### 3.4 Raw fallback is sacred
If `parseRelevant(existing).isRawFallback` is true AND `parseRelevantGrouped` also can't decompose it, chaining is disabled entirely; the builder shows the raw-fallback banner, keeps the existing text **visible and editable** (never blanks it), and offers "edit as text" / "clear to use builder". No silent overwrite.

### 3.5 `× start over` is byte-safe
Clears reducer state only; it **never calls `setColumn`/`setExtra`**, so `row.extras[column]` is untouched until `+ insert` fires. (Verified by Playwright reading saved bytes via the API — see §7 Slice 2 e2e.)

**`setExtra` delete-on-empty caveat (verified at FormEditor.tsx:692-699):** `setExtra` *deletes* `row.extras[key]` when `value === ''` (line 695) rather than writing an empty string. Consequences for this plan:
- The reducer's `insertAll` path routes writes through `setColumn → setExtra`. It must **never** hand `setExtra` an empty string for the active column unless the user intends to clear it — clearing is a delete, which is fine and round-trip-safe, but the builder must not accidentally emit `''` for a non-empty build.
- The cancel-safety e2e (§7) asserts byte-identity at the **XLSForm-serializer level** (parser-level diff via the API), NOT a naive string compare of a possibly-absent key. If a column legitimately held a present-but-empty `''` originally, the editor normalizes it to absent on any write; this is **pre-existing XLSForm-serializer behavior** (a deleted key serializes identically to a previously-absent one for `relevant`/`calculation`/`constraint`/`choice_filter`), so the cancel-safety test must not falsely flag it. `× start over` sidesteps the whole issue by never writing at all.

### 3.6 Choices broadening is read-only
`parseXlsForm` on contact forms is ephemeral; no XLSForm bytes change as a result of contact-form scanning.

### 3.7 Legacy flat-mixed path must be fully removed (Slice 2 regression check)
Today `UnifiedConditionBuilder.build()` (FormEditor.tsx:1128-1143) returns bare ` and `/` or ` fragments and `doInsert` string-concatenates them, which **can already emit flat-mixed `a or b and c` straight to `row.extras[column]`** without going through any parser. Slice 2 replaces this path. The acceptance check (§7) requires confirming the fragment-append-connector path is **deleted**, and that ALL writes to `row.extras[column]` from the builder go through `serializeAnyParsed` (never a hand-concatenated connector). A reducer/e2e assertion verifies that no sequence of UI actions can produce a `row.extras` value where `parseRelevant(value).isRawFallback` became true due to flat-mixed connectors introduced by the builder itself.

### Breaking-change safety (the proposal's central defect — CORRECTED)

The proposal §5 and §9.2 claim the parser change is "widen `parseRelevant` return to `AnyParsed = ParsedExpression | GroupedExpression`". **This is wrong and a hard reject.** Verified against the real call-sites:

- `client/src/ui/RelevantRuleBuilder.tsx:37` — `useState<ParsedExpression>(() => parseRelevant(props.value))`; line 38 same; line 42 `setParsed(parseRelevant(...))`; the `{...parsed, rules}` spreads at lines 48/51 depend on the shape staying byte-identical.
- `client/src/ui/CalculationBuilder.tsx:54` — `condition: parseRelevant('')`; line 173 `condition: parseRelevant(v)`; line 184 `serializeConditionSummary(cond: ParsedExpression)`; line 208 `serializeRelevantStub(cond: ParsedExpression)`.
- `client/src/ui/DecisionsView.tsx:438` — `relevantToHumanLines(cond: ParsedExpression)`.
- `shared/src/xlsform/calculationBuilder.ts:21` — `condition: ParsedExpression` field type; line 50 `serializeRelevant(r.condition)`; line 67 `parseRelevant(cond)` bound to it.

Widening `parseRelevant`'s return type to a union breaks the typed slots above at compile time (GroupedExpression is not assignable to ParsedExpression). **Mandated fix:** keep `parseRelevant(expr): ParsedExpression` and `serializeRelevant(parsed: ParsedExpression): string` byte-identical. Add a NEW export `parseRelevantGrouped(expr): AnyParsed` that only the new FormEditor builder calls, plus `serializeAnyParsed(parsed: AnyParsed): string`. `shared/src/index.ts` re-exports `./xlsform/relevantParser.js`, so new exports are zero-config.

**HARD RULE (not optional):** do NOT add any new *required* field to `ParsedExpression`. Discriminate `AnyParsed` via `'subgroups' in parsed`. Adding a required `kind:'flat'` to `ParsedExpression` would break the `{...parsed, rules}` spreads at RelevantRuleBuilder.tsx:48/51 — so it is forbidden. `typecheck` green on all 5 consumers is the proof gate.

Result: the union is genuinely additive; the 5 consumers and all 85 shared tests stay untouched.

## 5. Data shapes

### Reducer state (transient, NOT persisted — `SurveyRow.extras` stays `Record<string,string>`)

```ts
type Clause = {
  field: string;
  op: '=' | '!=' | '>' | '<' | '>=' | '<=' | 'selected' | 'not' | 'ref' | 'today';
  value: string;  // empty for ops in {'ref','today','not'}
};
type Connector = 'and' | 'or';
type Subgroup = { clauses: Clause[]; connector: Connector };  // intra-subgroup, same combinator

interface BuilderState {
  column: 'relevant' | 'calculation' | 'constraint' | 'choice_filter' | '';
  clauses: Clause[];               // flat single-combinator chain (common case)
  connectors: Connector[];         // length === max(0, clauses.length - 1)
  draft: Clause;
  lockedConnector: Connector | null;
  groups: Subgroup[] | null;       // null = flat mode; non-null = grouped (two levels max)
  outerConnector: Connector | null;
  activeGroupIndex: number | null;
  rawFallback: string | null;      // non-null = chaining disabled, text preserved verbatim
}
```
